## 1. レビューの進め方

AIが書いた設計書は、見た目が整っていても中身に問題があることがあります。そこで、次の流れで確認しました。

```
① AIが設計書を作成（PR #2）
② AIが自分の設計書を点検し、「気になる箇所」をヒントとして出す（答えは出さない）
③ 人がヒントと業務知識をもとにレビューし、問題と直し方を判断する
④ AIが指摘どおりに修正（PR #3）
⑤ 人が修正内容を確認してマージ
```

**レビュー観点**：業務に合っているか／抜け漏れ／前後の矛盾／実現できるか／仕様の決めつけ／例外ケース

## 2. 指摘一覧

| No | 対象 | 指摘内容 | 分類 | 対応 | 確認 |
|---|---|---|---|---|---|
| 1 | 取込フォーマット | 業務の流れに「在庫戻し」があるのに、**返品理由**がない。在庫に戻すか（良品）、廃棄・メーカー返品か（不良）を判断できない | 業務の抜け漏れ | 返品理由（M列）と良品不良区分（N列）を追加。良品/不良はAIに推測させず人が選ぶ（要件 F3） | PR #3 |
| 2 | 要件定義書 F6 | 「OCR結果をこのままでOKと確定する」とあるが、**今のアプリにその機能がなく**、確定の操作方法もどこにも定義されていない | 実現性・定義漏れ | F7「確定操作」を追加（確定の単位・条件・取り消し）。状態に「確定済み」「出力済み」を追加 | PR #3 |
| 3 | 要件定義書 C3 | 「数量×単価＝金額」は、**値引き行や単価の端数**では成り立たない。正しい伝票までエラーになる | 例外ケースの考慮不足 | 値引き行をチェック対象外にし、許容差（1円）つきの警告に変更 | PR #3 |

| 5 | 取込フォーマット | 伝票区分 `20`・数量をプラスで出す などを、**取込先の仕様を確認せずに決めている** | 仕様の決めつけ | 7章「要確認事項」Q1〜Q8 を追加し、該当する列に「要確認」を表示 | PR #3 |

## 4. わかったこと（AIの成果物の傾向）

- **業務の現場の事情に弱い**：返品理由のように、実際の業務を知っていれば当然必要な項目が抜けやすい。業務経験のある人のレビューが必要
- **「書いてあるが、決まっていない」ことがある**：機能や保存先を、定義しないまま前提として使ってしまう
- **確認が必要なことでも、自信を持って決めてしまう**：取込先の仕様のように、お客様に確認すべき内容を仮の値で確定させてしまう
- **きれいな「正常パターン」で考える**：値引き・端数のような例外が抜ける

**今後の対策**：AIに設計書を作らせるときは、最初に「業務の流れ」と「未確定の仕様は要確認事項として分けて書くこと」を指示する。レビューでは上の観点表で確認する。
