# 返品伝票OCR テスト仕様書

- 対象：要件定義書 1.4版（F1〜F9）と Issue #19 の精度向上（2026-11-06 時点、Issue #23）
- 自動テスト：`tests/` の pytest **162件**。`.venv\Scripts\python -m pytest -q` で実行。GitHub に push すると GitHub Actions（`.github/workflows/tests.yml`）が同じテストを実行し、README のバッジに結果が出る
- OCRエンジン（EasyOCR）は自動テストでは使わない。偽の reader（決めた答えを返す）に置き換えて、**OCRの前後の処理**を確かめる。OCRそのものの正解率は別に計測する（4章）
- 関連：[要件定義書](要件定義書.md) / [基本設計書](基本設計書.md)

## 3. テストの書き方の決まり

- **テスト名は日本語の文**にする（例：`test_1行でもエラーがあれば何も取り込まない`）。失敗したとき、何が守られていないかが名前だけでわかるようにする
- 要件定義書の番号や Q&A の番号を名前に入れる（例：`test_16_エラーがあると確定できない`、`test_18_列の並びと見出しとシート名が定義書どおり`）
- **1つのテストで1つのこと**を確かめる。前提のデータ作りは `tests/helpers.py` と `conftest.py` にまとめる
- ファイルやDBは **一時フォルダ**に作り、テスト後に消す。`records/` や `returns.db` には触らない
- OCRは偽の reader に置き換える。EasyOCR の読み方そのものはテストしない（4章で計測する）
- 新しい要件・直した不具合には、先にテストを足してから実装する（Issue #19 では読み直しのテスト8件を先に書いた）

## 4. OCRの正解率の計測（自動テストとは別）

OCRエンジンの読み方は入力の画像次第で変わるため、「正しいか」ではなく「どれくらい正しいか」を測る。

| 項目 | 内容 |
|---|---|
| 道具 | `tools/make_benchmark.py`（正解つきの架空伝票を生成）、`tools/ocr_benchmark.py`（読んで正解率を集計） |
| 伝票 | 10枚 × 3種類（きれい／スキャン風：傾き・にじみ・ノイズ／小さい文字）＝30枚。乱数の種を固定し、毎回同じ伝票 |
| 判定 | アプリと同じ判定（services/review.judge）。全角半角・空白・カンマの表記ゆれは正解に数える |
| 出力 | `docs/test_reports/OCR精度_<tag>_<日時>.md`（項目ごとの正解率と、間違えた欄の一覧） |
| 結果 | 直す前 54.2% → 直した後 97.4%（[要件定義書 F3.1](要件定義書.md)）。残る誤りはスキャン風の返品理由など、人が確認する欄 |
| 使い方 | 読み取りの処理を変えたら、同じ `--count --seed` で測り直し、前の結果と比べてから採用する |

## 5. 手で確認する項目（自動化しないもの）

自動テストで確かめにくい「見た目」と「実際のOCR」は、PRを出す前に手で確かめる。

| No | 確認すること | 手順 | 期待 |
|---|---|---|---|
| M1 | サンプル伝票が正しく読める | アプリを起動し `samples/返品伝票_サンプル.pdf` を読み込む | 見出し5項目と明細3行が正しい。黄色の欄が「良品/不良」「3行目の区分」だけ |
| M2 | スキャン風の伝票でも崩れない | `records/benchmark/bench_01_scan.pdf` を読み込む | 行数が合い、数字の列が隣にずれない |
| M3 | 入力欄の操作だけで確定まで進める | キーボードだけで欄を移動し、良品／不良・区分・税率を選ぶ | Tab で順に移動でき、黄色が消えて「確定できます」になる |
| M4 | 画像の枠と入力欄が対応している | 右の入力欄にポインタを乗せる | 左の画像に、その欄の枠が出る |
| M5 | マスタ取り込みのエラー表示 | 列名を1つ変えたExcelを取り込む | 何行目の、どの列が、なぜダメかが読める。件数は増えない |
| M6 | 出力先フォルダ | 無いフォルダを指定して出力 | フォルダが作られ、お知らせが出る |
| M7 | 他サイトからの操作 | 別のページから fetch で `/api/docs` を叩く | 403 で断られる |
